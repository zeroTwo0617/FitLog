# FitLog V1 发布计划

## 目标

V1 的目标不是一次性做完所有功能，而是发布一个数据可信、核心流程稳定、可以持续迭代的个人训练记录小程序。

V1 必须保证：

- 用户可以创建计划、记录训练、查看历史和统计。
- 训练数据不会因为页面刷新、重复点击或网络重试而明显重复或丢失。
- 统计图表与产品定义一致，用户能理解“为什么有数据/为什么没有数据”。
- 用户数据按 `_openid` 隔离，导出数据只包含当前用户数据。
- CloudBase 配置、云函数、索引和权限可以被重复部署和验收。

## V1 范围

### 必须上线

- 首页概览
- 动作库和训练计划
- 训练记录保存
- 历史记录和单次训练详情
- 日历
- 训练统计和 1RM 趋势
- 身体数据
- 饮食记录
- 用户档案初始化
- 数据导出
- 基础教练 Agent

### 暂不上线或限制为开发功能

- `seedData` 测试数据入口已移除
- 未完成的社交、分享、排行榜功能
- 多设备冲突合并
- 复杂离线同步
- 面向公众的医疗或营养诊断

## 发布阻断项

以下任意一项未完成，都不发布 V1：

- `app.js` 启动无异常，CloudBase 环境可连接。
- 所有生产云函数已经部署到当前 `CLOUD_ENV`。
- 所有用户集合权限为“仅创建者可读写”。
- [cloudbase-indexes.md](../operations/cloudbase-indexes.md) 中的索引已经在控制台确认。
- 训练保存事务在真实设备上验证成功。
- 训练统计、容量、最大重量和 1RM 与明细数据人工核对一致。
- 导出数据不包含其他用户记录。
- 生产版本无测试数据入口（`seedData` 已移除）。
- 关键错误不会被静默吞掉，也不会向用户暴露内部堆栈。

## 阶段一：冻结数据口径

### 1.1 训练完成规则

V1 采用以下规则：

- 保存训练后，`workouts` 代表一次真实训练，训练日立即计入历史、日历和打卡统计。
- 只有 `completed === true` 的组计入训练容量、最大重量和 1RM。
- 记录页必须明确显示“勾选完成后才计入统计”。
- 对旧数据缺少 `completed` 字段的组，兼容为已完成。
- 自重动作不能因为 `weight = 0` 就完全消失；V1 至少在训练次数和动作统计中保留，容量图可以标记为不计算负重容量。

### 1.2 日期规则

- `dateStr` 是用户选择的本地训练日，格式固定为 `YYYY-MM-DD`。
- `date`、`createdAt`、`updatedAt` 是服务端时间戳，用于排序和审计。
- 统计窗口必须明确锚定“今天”还是“最近一次训练日”，不能由不同页面各自决定。

### 1.3 统计图规则

- 无有效数据时显示空状态，不显示误导性的 0/1 轴。
- 训练量图的纵轴使用真实最大训练量，并对小数值做合理刻度处理。
- 1RM 图只显示该动作有有效数据的日期；无数据日期显示断点或空状态。
- 动作匹配优先使用 `exerciseId`，名称只作为展示字段，避免改名后历史断裂。
- 页面展示值必须能从 `workouts + sets` 明细复算出来。

## 阶段二：修复核心数据链路

### 2.1 训练保存

- 保留 [saveWorkout](../cloudfunctions/saveWorkout/) 事务写入。
- 增加请求幂等键，防止用户重复点击或网络重试创建两次训练。
- 服务端限制动作数、组数、次数、重量和文本长度。
- 保存成功后只使用云函数返回的 `workoutId` 更新页面。
- 失败时保留可重试状态，不显示“已保存”。

### 2.2 身体数据

- 同一用户同一天默认更新已有记录，而不是无限新增。
- 服务端保留范围校验和服务端时间。
- 页面显示最新记录时按 `dateStr` 和 `updatedAt` 稳定排序。

### 2.3 计划和饮食

- 计划和饮食写入继续全部走云函数。
- 更新或删除不存在的 ID 时返回明确错误，不把 0 条更新当成成功。
- 客户端校验与云函数校验建立同一份字段规则，避免规则漂移。

## 阶段三：统计和显示验收

为统计页建立固定测试数据集，至少覆盖：

- 一次训练包含已完成组和未完成组。
- 自重动作、空重量和有重量动作。
- 同一动作多天训练。
- 动作名称变化但 `exerciseId` 不变。
- 旧数据缺少 `completed` 字段。
- 最近 14 天没有数据、只有一天数据、多天数据。
- 同一天多次训练。

每个场景都要同时核对：

1. 训练记录详情。
2. 历史列表。
3. 日历训练日。
4. 统计训练量。
5. 最大重量。
6. 1RM 趋势。

任何一个页面口径不一致，都视为未通过。

## 阶段四：性能和数据访问

- 页面只能调用 `miniprogram/utils/repositories/`。
- 不允许页面直接调用 `wx.cloud.database()`、`.collection()` 或 `wx.cloud.callFunction()`。
- 统计、日历和 Agent 不长期读取全部历史数据；优先增加按日期范围的查询或云端聚合。
- `getAll()` 只用于小规模数据、导出或明确需要完整数据的场景。
- 所有云函数的 `wx-server-sdk` 使用固定版本，不使用 `latest`。
- 所有列表查询都定义排序字段，避免同一时间数据顺序不稳定。

## 阶段五：安全和 CloudBase 配置

### 云函数

生产环境需要部署：

```text
agent
ensureUser
updateUserActive
saveWorkout
savePlan
deletePlan
saveBodyMetric
saveNutritionLog
deleteNutritionLog
exportData
```

### 数据库

- 集合权限全部按用户隔离。
- 索引按 [cloudbase-indexes.md](../operations/cloudbase-indexes.md) 配置。
- 管理员权限云函数必须显式按 `_openid` 过滤。
- 导出、删除、更新接口都必须验证资源属于当前用户。

### 配置

- `CLOUD_ENV` 与目标发布环境一致。
- `project.config.json` 的 `miniprogramRoot` 和 `cloudfunctionRoot` 与目录一致。
- `project.private.config.json`、模型密钥和本地配置不提交 Git。
- 生产环境关闭不必要的调试日志和测试入口。

## 阶段六：测试和发布

### 自动化检查

- 所有页面和云函数 JavaScript 语法检查通过。
- 所有 Node 测试脚本通过。
- 统计纯函数测试通过。
- 数据访问 Repository 的成功、失败和空数据测试通过。
- 云函数契约测试覆盖成功、未登录、越权、非法字段和重复请求。

### 真机验收

- Android 和 iOS 至少各验证一次。
- 新用户首次启动、首次保存训练、返回首页、再次打开历史全部正常。
- 弱网下重复点击保存不会产生重复训练。
- 退出/重新进入小程序后用户数据仍然正确。
- 空数据、加载中、加载失败和无权限状态均有可理解提示。
- 统计截图中的数据与明细逐项核对。

### 发布顺序

1. 部署并验证 CloudBase 云函数。
2. 配置并验证数据库权限和索引。
3. 上传体验版。
4. 用真实微信账号走完整验收清单。
5. 修复阻断问题后冻结版本号。
6. 提交审核。
7. 发布后观察云函数错误、保存失败率和用户反馈。

## V1 完成定义

只有同时满足以下条件，才标记 V1 完成：

- 核心训练流程真实设备通过。
- 统计口径已经书面确定并通过固定数据集验证。
- 所有用户数据访问经过 Repository 或受控云函数。
- 没有生产测试入口。
- CloudBase 配置已经在目标环境确认，而不是只存在于文档。
- 发布版本可以从干净目录重新导入并运行。

## V1 之后

V1 发布后再考虑：

- 云端统计聚合和缓存。
- 多设备冲突解决。
- 离线记录和补偿同步。
- 更细的训练计划周期化。
- Agent 的真实个性化推荐和可解释反馈。
